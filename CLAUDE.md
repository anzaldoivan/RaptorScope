# CLAUDE.md

RaptorScope is a native Win32 + OpenGL 1.1 viewer/editor for Dino Crisis (1999 PC) `.DAT` archives. It covers rooms (RDT), EMD characters, textures, palettes, VAG/SEQ audio, SCD scripts, saves and MPEG video, with OBJ/SMD/GLB export. It also opens the decoded parts of Dino Crisis 2 (PC): packages, textures, models, and a room's collision, zones and script (see **Dino Crisis 2** below). This repo (`DexeTech/RaptorScope`) is a fork of `coreynguyen/RaptorScope`. Work happens on `dev`, and PRs go to `main`.

[README.md](README.md) is the reference for file formats, SCD opcodes, overlay colours and key bindings. [EXPORTING.md](EXPORTING.md) covers GLB export. [TODO.md](TODO.md) lists unimplemented menu items. Read the relevant README section before changing a parser.

## Architecture

The code is in three layers: `core/` → `formats/` → `ui/`. `core/` and `formats/` don't use Win32. `video.h` is the exception, because it includes `<windows.h>`.

- **`core/`**: shared types (`types.h`), Capcom LZSS (`lzss`), BGR555 colour (`color`), and VAG ADPCM, Gian (SNDH) and SEQ decoding (`audio`).
- **`formats/`:**
  - `dat` is the archive.
  - `texture` does the VRAM deswizzle and the 4/8/16bpp CLUT rendering, and composes the 3D viewer's atlas (`build_texture_atlas`; `atlas_face_uv` maps a face into it).
  - `mesh` covers RDT layout, the room/door/EMD parsers, SCD script scanning for the overlay, animation, camera shots and OBJ/SMD/GLB export. It is the core of the reverse-engineering work.
  - `scd` is the disassembler shown in the SCD panel (F4).
  - `tim` handles TIM/IMD images, `save_editor` handles save files and `video` handles MPEG.
  - `dc2_room`, `dc2_scd` and `dc2_model` (one header, `dc2.h`) read Dino Crisis 2.
- **`ui/`:**
  - `app.cpp` has the window, theme and menus, the archive tree, entry classification and the atlas upload (`upload_archive_texture`: cache, GL size limit, UV editor crop).
  - `panels.cpp` has every panel's paint and input code. The largest is `ViewerPanel3D`: rendering, overlay, camera shots, walk mode and picking.
  - `uv_editor.h` and `about_dialog.h` are self-contained, header-only modals.
- `about_audio.h` and `about_banner.cpp` are generated byte arrays. Don't read them.

### Data flow

1. `dat_parse_file` loads the file into `DatArchive::raw`. Each `DatEntry::data` points into that buffer (not owned) unless `owned` is set, which happens after a replace.
2. `App::build_tree` classifies entries. For LZSS0, `classify_lzss0` probes for an RDT scene, a room/door mesh, an EMD, MIPS code or weapon data. Each tree item's `lParam` holds the entry index in its low 16 bits and a sub-selector in bits 16–23: 0 is auto, 1 is the static mesh, and ≥2 is EMD ordinal + 2.
3. `on_entry_select` in `app.cpp` switches on the entry type, fills one of the global panel singletons and calls `switch_panel`. The singletons (`g_hex`, `g_image`, `g_viewer3d`, …) are defined in `app.cpp` and declared `extern` in `panels.cpp`.

### Room pipeline (LZSS0 RDT)

1. `dat_entry_payload` decompresses the entry. ST50B and ST60E store their RDT raw as type 0 (`is_raw_rdt_entry`).
2. `parse_rdt_overlay` walks or scans the SCD and fills `RdtSceneOverlay`.
3. `mesh_apply_xforms` builds **only the sections that scripts place** (0x23, and the item models of 0x28 type-4 zones). Sections that are never placed are appended with `MeshTri::alt = 1`. The viewer hides them unless H is pressed, and GLB export skips them.
4. The code collects each face's tpage and CLUT, then calls `upload_archive_texture` and `set_mesh`. It then calls `overlay_floor_heights` and `set_overlay`, and finally `g_scd.load`.

### PSX conventions used everywhere

- **Load address of an LZSS0 entry:** if `y & 0x8000` is set, `base = ((y & 0x7FFF) << 16) | x | 0x80000000`. Rooms normally use `0x80100000`. Pointers inside the blob minus `base` give file offsets.
- **Viewer coordinates:** `(-x, -y, z)` of game coordinates, which are Y-down. Triangle winding is reversed to match. Angles use 4096 = 360°. One game unit is about 1 mm.
- **tpage:**
  - `tx = tp & 0xF` (in units of 64 halfwords)
  - `ty = (tp >> 4) & 1`
  - `abr = (tp >> 5) & 3`
  - depth = `(tp >> 7) & 3`, where 0 = 4bpp, 1 = 8bpp, 2 = 16bpp
- **CLUT:** `x = (clut & 0x3F) * 16`, `y = (clut >> 6) & 0x1FF`.
- **Atlas:** `ViewerPanel3D::slice_map[row * 65 + slot]` gives a compact slice for each CLUT row. Slot 0 is 8bpp and slots 1–64 are the 4bpp sub-palettes, kept separate so 4bpp and 8bpp never collide.

### Dino Crisis 2

DC2 is detected by content, in `dat_parse_memory` (`DatArchive::is_dc2`): its header entries are 32 bytes. Its type numbers 5 and 6 are parsed as `DAT_LZSS0` and `DAT_LZSS1`, so the DC1 code for compressed data and textures applies; `DatEntry::raw_type` keeps the number from the file and `load_base` the address the entry loads at. The DC2 readers fill the DC1 structures (`EmdModel`, `Mesh`, `RdtSceneOverlay` with `dc2 = 1`, `ScdDisasm` with `dc2 = true`), so the viewer, the overlay tree and the exporters need little DC2 code: `App::build_tree` and `on_entry_select` each branch once, to `dc2_tree_add` and `dc2_entry_select`.

- **Source of the formats.** The dinorand project's documents and tools, cited in comments by registry row (`K<n>`) or file name where a DC1 comment would cite a DINO.exe address. The viewer reads no executable. README's **Dino Crisis 2** sections list what is and is not decoded. Do not add a DC2 format from a guess: it has to be in dinorand's documents or checked on every file of the game.
- **Where the code departs from dinorand, on purpose.** Slot 2's header, the vertex-to-bone rule, quad order, the `.TEX` layout and the 4096 limit on a part's offset; each is explained in a comment where it is read and listed in [DC2-DINORAND-HANDOFF.md](DC2-DINORAND-HANDOFF.md).
- **Unit tests** (no game needed):
  ```sh
  g++ -std=c++11 -Iinclude -D_snprintf=snprintf tests/test_dc2.cpp src/formats/dat.cpp src/formats/dc2_room.cpp src/formats/dc2_scd.cpp src/formats/dc2_model.cpp src/formats/texture.cpp src/formats/mesh.cpp src/core/lzss.cpp src/core/color.cpp -o test_dc2 && ./test_dc2
  ```
- **Corpus check** (needs the game and a dinorand checkout; prints `SKIPPED` and exits 0 without them):
  ```sh
  g++ -std=c++11 -O1 -Iinclude -D_snprintf=snprintf tests/dc2_corpus.cpp src/formats/dat.cpp src/formats/dc2_room.cpp src/formats/dc2_scd.cpp src/formats/dc2_model.cpp src/core/lzss.cpp -o dc2_corpus
  DINORAND_DC2_DIR=<install> ./dc2_corpus > corpus.tsv
  DINORAND_ROOT=<dinorand> python3 tests/check_dc2_corpus.py corpus.tsv
  ```
  It compares every package, entry, room record and model with dinorand's readers and ends with a table of totals against the documented figures. Run it after any change to `dat.cpp` or a `dc2_*.cpp`. Never commit its output: it is derived from game files.
- **Textures.** A DC2 archive goes through the same atlas and image-panel code as DC1, with three differences, each behind `is_dc2`: 4bpp sub-palettes are counted from the texture's own palette, a texture with no palette after it takes the one at the CLUT's position, and index 0 at `0x8000` stays opaque. `tests/test_dc2.cpp` runs each case as a DC1 archive too. A change to `build_texture_atlas` must leave the DC1 atlas byte-identical; there is no test for that in the repo (it needs the game), so hash the atlas of every room and character before and after.
- **The viewer side is build-checked only.** Nothing DC2 has been looked at in the running program yet; B40–B43 say what to look at.

### Naming traps

The README and the scanners in `mesh.cpp` hold the current understanding of the formats. Some struct names, opcode mnemonics and comments are older and wrong; C1–C6 under Known issues list them. Check those before trusting a name or a comment. The most common trap (C1): `RdtItemSpawn`/`overlay.items` holds 0x5B **enemy spawns**, and `RdtEnemySpawn`/`overlay.enemies` holds 0x42 **objects**.

When you establish a format fact, cite the DINO.exe handler (for example `sub_426806` or VA `0x6576A0`) in a comment, and check it across every room where you can, as existing comments do.

## Code style

- **Language level:** C-style C++, with C++11 as the floor. The UI uses lambdas and `{}` init, despite the README's "pre-C++11" claim. It must build with both MSVC and MinGW and target XP-era Win32 (`WINVER 0x0501`).
- **Containers:** no STL, exceptions or RTTI outside `emd_glb.inc`. Use `Buffer`/`Array<T>` from `types.h` (non-copyable), `malloc`/`free`, fixed-capacity arrays with `MAX_*` constants and `_snprintf`.
- **POD only:** `Array<T>` uses `realloc` and never runs constructors, so `T` must be POD. `RdtSceneOverlay` zero-fills itself with `memset(this, …)`, so keep it POD and bounds-check its fixed arrays.
- **Comments:** follow the existing style: `/*═══…═══*/` file and section banners, `/*─── Name ───*/` sub-headers, and plain-prose comments that say what the game does, with a room as an example.
- **Read-only files:** don't reformat or convert line endings. The index is LF and `core.autocrlf=true`. Don't touch vendored or generated files.

## Commits and docs

- Commit subjects look like `Area: what changed, lowercase` (for example `3D viewer: …`, `Rooms: …`, `Overlay: …`, `GLB export: …`, `README: …`). Bodies are prose: what the game does, which rooms showed the problem, and DINO.exe addresses.
- User-visible features and key bindings go into README.md, usually as a separate `README:` commit. Changes to export behaviour also update EXPORTING.md.

## Releases

A release is the zip `bin\RaptorScope-DC1-GLB-win64.zip`. `bin/` is git-ignored, so the zip is never committed. It holds six files:

| File | Source |
|---|---|
| `RaptorScope-DC1-GLB.exe` | `bin\Release_x64\DC_Archive_Tool.exe` from the MSBuild command under **Build**, renamed |
| `dc1_export.exe` | The command-line GLB exporter, built with `cl` (step 3) |
| `README.md`, `EXPORTING.md`, `LICENSE` | The repo root, as committed |
| `RELEASE_NOTES.md` | Written for each release; it replaces the previous one and isn't kept in the repo |

Both exes are MSVC x64 builds with the static runtime (`/MT`), so they need no extra DLLs. `build-windows.cmd` builds the same pair with MinGW, but MinGW isn't installed here.

**Steps:**

1. **Clean tree.** Commit and push everything on `dev` first, so `git status` is empty and the release matches a pushed commit.
2. **GUI.** Close RaptorScope, then run the MSBuild command from **Build** with `/t:Rebuild` added.
3. **CLI.** In a scratch folder, from cmd.exe:
   ```bat
   call "C:\Program Files\Microsoft Visual Studio\18\Insiders\VC\Auxiliary\Build\vcvars64.bat"
   cl /nologo /O2 /MT /EHsc /W3 /D_CRT_SECURE_NO_WARNINGS /I E:\RaptorScope\include E:\RaptorScope\tools\dc1_export.cpp E:\RaptorScope\src\formats\dat.cpp E:\RaptorScope\src\formats\mesh.cpp E:\RaptorScope\src\formats\dc2_model.cpp E:\RaptorScope\src\core\lzss.cpp /Fe:dc1_export.exe
   ```

   Run with no arguments, it should print its usage line and exit with code 2.
4. **Notes.** Write `RELEASE_NOTES.md`, following the rules below.
5. **Package.** Copy the six files into a scratch staging folder, and copy the old zip to scratch as a backup. Then replace the zip with `Compress-Archive -Path <the six files> -DestinationPath bin\RaptorScope-DC1-GLB-win64.zip -Force`, and list its entries to check all six are there.

**Release notes:**

- **Audience.** Write for people who use the tool to view and export Dino Crisis files, not for developers. Say what they will notice, with rooms and keys as examples. Leave out function names and Known-issues IDs.
- **Coverage.** Cover every commit since the last release. The notes end with `Built from <hash> on dev.`; for the next release, `git log <hash>..HEAD` lists what's new. The 2026-10-05 build recorded no hash; it was built from `2e77ded`.
- **Format.**
  - Title `# RaptorScope DC1 GLB: <YYYY-MM-DD> build`, then a short summary paragraph.
  - One section per area (for example 3D viewer, Room overlay, Export, Editors), each a list of bullets with a bold lead-in.
  - Build and packaging changes go last, under **Package**.

**Tags and GitHub releases.** Tags `v1`–`v1.2` (2026-10-02 to 10-04) point at `main`. The zip builds since then aren't tagged. Create a tag or a GitHub release only when the user asks, since both publish; `gh` isn't logged in on this machine.

### Bugs

Ordered with memory safety and data loss first.

- **B3** **Weapon aim block is read as the wrong shape (verify).**
  - The block is four 8-byte vectors `{x, y, z, pad}` that form a trapezoid in x and z. The editor reads the low s16 of each 4-byte slot, so it shows x and z; the halves it skips are y and the pad, not a sign extension, and it writes back only the halves it read.
  - Its labels (`aim_neg_x`, `aim_base`, `aim_far`…) are guesses.
  - The six "camera offset" values start 6 bytes before where the panel reads them (`aim_off + 26`, not `aim_off + 32`).
- **B4** **Save editor out-of-bounds read.** `dc_save_build` indexes its 10-entry digit table with `hours/10`. The Play Time edit has no length limit, so 100+ hours reads past the table.
- **B5** **`new[]`/`free` mismatch.** `parse_standalone_emd_mesh_dec` fills `mesh.verts/tris` with `new[]`, but `Mesh` frees with `free`, and existing arrays are overwritten without being freed. Use `mesh.alloc`.
- **B6** **Dangling pointer after a failed `realloc`.** `mesh_apply_xforms` returns without storing the moved pointer when one of its two `realloc`s fails after the other succeeded. `mesh.verts` or `mesh.tris` is then left dangling.
- **B8** **WAV buffer leak.** `AudioPanel::load_wav` stores its PCM in `pcm_data`, but `free_samples()` and the destructor free only `samples[i].pcm`.
- **B12** **SMD skeleton doesn't line up with the mesh.** `export_emd_smd` writes bone offsets in game axes but vertices in viewer axes (x, y, z negated). Any non-zero bone with parent 0xFF is written with parent 255.
- **B13** **3D view can show stale textures.** `build_archive_atlas` (`app.cpp`) caches the atlas by the `DatArchive*` address plus the CLUT list. `close_archive` doesn't reset that cache and Import/Replace doesn't invalidate it. A reopened archive allocated at the same address, or a replaced texture, can therefore show the old atlas. (likely)
- **B15** **Import/Replace and saving leave stale state.**
  - The tree isn't rebuilt, so labels and the `g_emd_info` EMD offsets reflect the old data, and the refresh drops the sub-selector.
  - Save As on an item bank writes the original `raw` bytes, silently dropping any replacements.
  - `dat_write_file`'s result is ignored.
  - `archive->modified` is never checked on close or exit.
  - Ctrl+S (`IDM_FILE_SAVE`) has no handler.
- **B17** **Blend modes are approximated wrongly.** `ViewerPanel3D::render` draws ABR 3 (B+F/4) with the same full-additive blend as ABR 1, and ABR 2 (B−F) as a multiply. The comments say quarter-additive and subtractive.
- **B18** **Blending decided from ABR alone (verify).**
  - The viewer (`build_mesh_lists`) and room GLB export (`export_room_glb`) treat ABR 0 as always opaque and ABR 1–3 as always blended.
  - On the PSX, a polygon is only semi-transparent if its command byte also has the semi-transparency bit; for room triangles that is byte +31, which `parse_rdt_layout` reads but no parser keeps.
  - ABR 0 is the 50/50 blend mode, so semi-transparent ABR 0 faces are drawn opaque.
  - A semi-transparent polygon blends only the texels whose STP bit is set and draws the rest opaque. ST108's lit wall plate (slot 2, face 7) is ABR 1 on a palette with no STP entries, so the viewer adds it to the scene where the game should draw it solid.
- **B19** **Character GLBs come out tinted.** `export_emd_glb` writes the per-part debug colours (`pcols` from `parse_emd_model_dec`) as `COLOR_0`, and glTF multiplies `COLOR_0` into the base colour. Room GLBs double `avg_colors`, which is already ×1.6, so they mostly saturate.
- **B20** **EMD hierarchies with a parent after its child.**
  - `parse_emd_model_dec` and the bind-pose restore in `anim_select_clip` read `abs_pos[parent]` before it is written when a parent's index is higher than its child's (uninitialised stack).
  - `decode_emd_pose` and GLB export reject such models instead.
  - The bind-pose restore also keeps the last animated frame's normals.
- **B21** **SEQ playback can use the wrong sound bank.** `AudioPanel::render_seq` uses the archive's last SNDB. Archives can hold several SNDH/SNDB pairs, which is why `find_sndb_gian` exists.
- **B22** **SEQ parsers lose sync.**
  - `parse_seq_notes` and `render_seq_to_stereo` skip one byte for 0xAn events, which carry two data bytes.
  - `parse_seq_notes` drops a note that is re-keyed before its note-off; the synth closes it instead.
  - Delta times are read as a single byte. (verify that they aren't variable-length)
- **B23** **Undefined shift in VAG decoding.** `decode_vag_block` shifts by `12 - shift`, which is negative for shift 13–15; the SPU treats those as 9. It also left-shifts negative values.
- **B24** **Mouse and keyboard state is lost.**
  - `Viewer3DProc` uses `LOWORD(lp)` (unsigned) instead of `GET_X_LPARAM`, so captured positions left of or above the window become ~65535.
  - Nothing handles `WM_CAPTURECHANGED`/`WM_KILLFOCUS`, so alt-tabbing during a drag or in walk mode leaves the cursor hidden (the `ShowCursor` count) and walk keys held down.
- **B25** **An empty placed section draws its neighbour (verify).**
  - The one-section loop in `mesh_apply_xforms` `continue`s past an empty header, so the next section is drawn with that placement.
  - Only the Y rotation is applied. The rx/rz values set by 0x23, 0x2A fields 6/8 and 0x37 are ignored.
- **B27** **Door meshes may render inside out (verify).**
  - `parse_door_mesh_dec` keeps the source winding, while the room parsers reverse it for the same axis flip.
  - Doors render through `set_mesh` with counter-clockwise culling, so their front faces may be culled.
  - `is_door_mesh_entry_dec` also builds the base address without `ex`.
- **B28** **3D atlas palette pairing (verify).** For a DC1 archive, `build_texture_atlas` pairs each texture with the next palette entry and counts 4bpp sub-palettes from the first palette's x for all of them. The 2D viewer instead finds each face's palette by CLUT position (`render_texture_by_faces`). In 3D, faces whose CLUT lives in a different palette entry get the wrong colours. DC2 archives count sub-palettes from the texture's own palette and fall back on the CLUT's position (B47 says why it is only a fallback); nothing has shown which rule DC1 needs.
- **B29** **UV editor shows the wrong palette rows.** `ShowUVEditor`/`Uve_RebuildTexDib` assume dense rows × sub-palette slices (`slice_h = atlas_h / (rows * subs)`). The atlas is actually the sparse `slice_map` layout with 512-row slices, so P shows the wrong regions when there are several CLUT rows.
- **B30** **Video and audio drift apart (verify).**
  - Frames advance on `SetTimer(1000/fps)`, which is truncated and has about 16 ms granularity, while audio runs on its own clock with no resync.
  - `decode_mpeg_video` doesn't check the first `audio_buf` malloc, and leaks on `realloc` failure.
- **B31** **Latent out-of-bounds reads in texture rendering.**
  - `render_16bpp` takes no buffer size, so `render_texture`'s 16bpp branch can't pass one.
  - `render_4bpp` without deswizzle checks `total_bytes` but not `pix_size`; `render_8bpp` checks both.
- **B32** **Camera-cut zone layout fits no room (verify).** `parse_rdt_overlay` reads a 16-byte header, 17 group descriptors of 16 bytes (288 bytes in all) and 20-byte zones from `ptr[2] + 272`, which also falls inside group 16. `ptr[3] - ptr[2] == 288 + 20 × (sum of the 17 group counts)` holds in none of the 148 rooms, so the camera-cut zones the overlay draws may not be zones.
- **B33** **Faces just behind another face in depth-sorted slots (verify).** `raise_recessed_faces` handles only render modes 2 and 3, where list order decides what is on top. In modes 0 and 1 the game sorts each face by its nearest or farthest vertex (DINO.exe 0x44DA6D), so whether a face slightly behind a larger parallel one shows depends on the camera; mode 1 likely shows it. The viewer always hides those faces. A rough survey of axis-aligned faces found up to 130 candidate pairs in mode 1 sections and 30 in mode 0.
- **B34** **Slots that only native code shows are drawn (verify).** Thread 0 (room start) hides some model slots with `48 03 <slot> 00`, and no script shows them again, so only DINO.exe's room code can. The viewer draws them anyway, at the position 0x23 gives. ST300's six card boards (slots 0–5, letters A–F) are hidden this way: card A is placed on a wall and cards B–F at (0,0,0), so B–F show stacked at the room origin, half under the floor. The native code that positions and shows them has not been found. 21 slots in 11 rooms are hidden like this (ST10F, ST205, ST300, ST30B, ST502, ST511, ST601, ST606, ST802, ST906, STC06).
- **B35** **Texture view dims texels that only 2D screens use (verify).** `render_texture_by_faces` dims every texel no face in the archive samples. Screens that DINO.exe draws in 2D, such as ST300's code-input screen (BACK/OK buttons, INPUT CODE / DISPLAYING THE CODE, letter tiles, a font, the blue band at the top of texture page 8 and all of page 9), have no faces, so they are dimmed and decoded with a guessed CLUT. Which draw code samples them, and with which CLUTs, has not been found.
- **B36** **0x3A is not a scene light (verify).** Across the 637 uses in the 148 rooms' threads, byte 1 is always 0 and byte 2 is 1–15 (214 of them have 1). The handler installs a behaviour on the bound character. `parse_rdt_overlay` still builds lights from it (slot = byte 1, subtype = byte 2), and `ViewerPanel3D` caches them as room lights. Because the slot is always 0 and only subtype 1 gets through, a room whose ptr[0] already gives a light 0 has that light's colour overwritten with bytes +4/+6/+8, and otherwise gets a positionless light.
- **B37** **Collision rect stride is unsettled (verify).** The 128-byte group index (16 × 8 bytes) fits, but `parse_rdt_overlay` reads 48-byte rects and the section lengths do not agree. `ptr[2] - ptr[1] == 128 + stride × (sum of the group counts)` holds in 52 rooms for 48 bytes and in 65 for 52, but 52 rooms have no rects at all and fit any stride; of the other 96, 48 bytes fits 5, 52 fits 18 and 56 fits 12. ST100 has one rect in a 180-byte section, which is 52 bytes.
- **B38** **Weapon editor records are shot entries, not weapon stats (verify).**
  - The 32-byte records are per-projectile entries. The game's fire routine spawns one projectile per record while the 32-bit word at record +4 equals a byte on the player, starting at an index held on the player. It reads only +0 (byte), +4 (word) and the halfwords at +0xC, +0xE, +0x10, +0x12, +0x16, +0x18 and +0x1A.
  - The panel's field names (Fire Mode, Ammo Type, Spread, Recoil, Power, Range, Blast…) and its per-record weapon names are therefore unsupported.
  - wep10–13 have a second record table after the pointer table, which the panel never shows.
- **B39** **Save editor key-item flags use the wrong store (verify).** `DC_FLAG_ITEMS` sets bit groups in the 96-byte event-flag window at gs+72. Held items are stored one bit per item id in a 32-byte bank at gs+240, outside that window. The listed bit sets are event flags that happen to change at those points in the game, so toggling one may not give or remove the item.
- **B40** **DC2 model orientation is assumed (verify).** `dc2_parse_model` negates all three axes, as the DC1 character parser does, and the viewer draws it with DC1's winding. No document states DC2's handedness. Open `E00.DAT` (with `E00.TEX` beside it): the raptor should stand upright, textured, not mirrored and not inside out. Rendered offline from the parser's output it is whole and correctly textured, which settles the bone, quad and UV rules but not mirroring.
- **B41** **DC2 model texturing in the viewer has never been seen (verify).** `dc2_show_model` hands `upload_archive_texture` the `.TEX` archive and one CLUT. Rendered offline, the atlas pages of E20, SC05, M_RESULT and the player skins come out whole; the model with its texture on it has not been looked at. Check `E00.DAT` and `E40.DAT`, each with its `.TEX` beside it, and `WEP_P001.DAT`. `WEP_P000.DAT` and `WEP_P100.DAT` have no skin page and take `WP00A.DAT` / `WP10A.DAT` as a stand-in (alternate skin, `dc2_alt_skin_name`): the game loads those only when a flag is set, and which file gives the default skin is unknown. 14 more packages have a model with no texture of its own and open untextured unless a `.TEX` of the same name is beside them: E00, E90, M_TITLE, RES00–02, SC08, SC09, SC11, SC19, SC40, SC41, SC46, SC49. Where the SC*, RES* and M_TITLE skins come from is not known.
- **B42** **DC2 door and item corners are read by analogy (verify).** dinorand documents the four (x, z) corners at record +4..+0x12 for triggers (0x31) only. `dc2_scd.cpp` reads the same record bytes for doors (0x30) and item pickups (0x35). Plotted offline, ST102's doors sit at the ends of its collision outline, which supports it. Check ST101's two doors (to ST102 and ST100) and an item room in the viewer.
- **B43** **The DC2 room view has never been seen (verify).** The view is framed by a mesh of zero-area triangles along the collision outline (`dc2_room_outline_mesh`), the overlay is switched on, and the overlay tree shows DC2 names. Check ST101 and ST102: something is visible on opening, the tree lists doors with destinations, selecting an item highlights it, and F4 lists the script.
- **B44** **Two DC2 collision records are longer than their points.** ST702's record 2 has 588 bytes and ST904's record 9 has 12 bytes beyond 12 + 8 x points; they are not read. The slot's second block (20-byte records, 54 of them in 10 rooms), a record's bytes +4..+7 and its per-point attribute words are not decoded either.
- **B45** **DC2 records with computed positions are not drawn.** `dc2_room_overlay` leaves out a door, trigger, item or spawn when a corner or coordinate is not a literal push. In ST102, 5 of 6 spawns take z from the room's global table (mode 6), which is in the file at slot 5 + 0x1C + the u32 at slot 5 + 0x0C (K64) and could be resolved.
- **B46** **Which palette a DC2 texture uses is guessed where no model samples it.** Depth comes from the palette's size (under 512 bytes is 4bpp, `palette_bpp`), and a texture a model of the same package samples is shown with that model's CLUT. Every other texture (all room textures: the room mesh is not decoded) is shown with the palette stored after it and its first sub-palette; Up/Down steps through the others. An enemy's `.TEX` opened on its own has no model, so its texture is not shown as its `.DAT` samples it.
- **B47** **M_RESULT.DAT's model names a CLUT that does not fit its texture (verify).** Its header has page (896, 256) and CLUT (0, 511). The texture on that page is a gold swirl whose own palette, stored after it, is at y = 510; row 511 holds the palette of the "RESULT" picture, and decoded with it the swirl is noise. The atlas therefore keeps a texture's own palette and uses the CLUT's position only when it has none, which is not what the hardware does. The package has three swirl pages (gold, silver, teal) and one model, and RES00–02's models name a page with no texture, so the game probably sets page and CLUT per rank at run time. The image panel's face mode does follow the header: entry 3 of M_RESULT.DAT shows as noise until C switches to its own palette. It is the only model of the 117 with a texture in their package whose CLUT is not on the palette after the texture (`check_dc2_corpus.py` lists them).

### Contradictions (code vs README, comments or other code)

- **C1** **Swapped struct names.** `RdtItemSpawn`/`ov.items` holds 0x5B enemy spawns, and `RdtEnemySpawn`/`ov.enemies` holds 0x42 objects.
- **C2** **Wrong opcode names in `g_scd_opcodes` (`scd.h`).**
  - `mesh.h` calls 0x3C a light colour, where README and `scd.h` say it is the model slot render mode. `scd.h` calls 0x3D unknown, where the overlay treats it as fog.
- **C3** **Operand decoding in `fmt_operands` (`scd.cpp`) disagrees with the overlay parser and README.**
  - 0x20: position at +4 instead of +8.
  - 0x3A: the subtype is ignored and xyz is read at +2 instead of +4 (and it is not a light at all, B36).
- **C4** **Two opcode-size tables disagree.**
  - The tables are `scd_inst_size`/`g_scd_opcodes` (`scd.h`) and `opsz` in `parse_rdt_scene_dec` (`mesh.cpp`).
  - `opsz` gives 0x04 one byte and treats 0x0A as a script end, where `scd_inst_size` gives both 4 bytes.
  - The 0x28 size table exists twice (`g_scd_op28_sizes` and `op28sz`), and the 0x5A rule (4 + 8 × byte 3) is now written out in both walkers.
- **C5** **Stale comments.**
  - `mesh.h`'s RDT block calls ptr[0] the "SCD main script table"; it holds lights and ambient.
  - `parse_rdt_overlay` has two stacked banners, one listing ptr[2] as camera data.
  - `MeshTri::alt` says "SCD branch variant"; it now means an unplaced section.
  - `ov_draw_zone` calls type 4 a door; it is an item pickup.
  - `mesh_apply_xforms` says it only adds non-zero placements on top of `parse_room_mesh_dec`.
  - `parse_rdt_scene_dec` claims inline sections start at 0x00 and that variants are merged by position; `alternate` is always false.
  - `export_room_glb` says "PSX units"; it writes metres.
- **C6** **Animation comments don't match the code.**
  - The banner above `decode_emd_pose` says the bitstream order is rx, rz, ry, that bytes 0–5 hold the root rotation, and that bones 1..N−1 are encoded. The code reads rx, ry, rz for bones 0..N−1 and ignores bytes 0–5.
  - Its step 4 says local × parent, while the code computes parent × local.
  - The "uv0→idx1, uv1→idx2, uv2→idx0" note in `parse_emd_model_dec` doesn't match the mapping the code uses (uv1→idx0, uv2→idx1, uv0→idx2).
  - The angle-sign flip applied when `n_anim_bones < n_parts` depends on the frame size that `extract_emd_anims` guessed, and nothing shows the `(4096 - v)` negation is right.
  - The six s16 before the rotations in an animation frame (bytes 0–11) look like root translation (words 0–2 follow the root bone's bind height) and accumulated travel (words 3–5 grow linearly from frame to frame, for example by −105 per frame in a walk clip of ST603's Therizinosaurus), not the entity rotation and velocity that the `decode_emd_pose` comment says. GLB export drops them (verify).
  - A clip's frame count is the stored count + 1 (in ST603, 48 of 48 gaps between the Therizinosaurus's 49 clips are exactly one frame). 71 of the 7081 clips in the 148 rooms (62 rooms; 56 are 4-frame clips such as ST100's at 0x1BDAC) have no valid extra frame and keep the stored count. Whether they are real clips, or their frame size is right, is unknown (verify). The frame size is still the largest candidate whose headers pass, and 123 clips changed size with the extra frame to validate (for example ST100's 2-frame clips at 104 or 84 bytes now read as 3 frames of 80).
- **C7** **Face colours are scaled more than README says.** README says 2× (`(tex*vtx)/128`), which the textured viewer now uses on each corner's colour (`MeshTri::vcol`). `avg_colors` (`mesh.cpp`) still multiplies by 1.6 and averages the corners into `MeshTri::color`, which the wireframe, the VM fallback path, faces without corner colours and room GLB export (B19) use, flat-shaded at about 1.6× or 3.2×.
- **C8** **Overlay colours don't match README and the legend.**
  - Zone type 3 is drawn mint, but README and the HUD legend say yellow.
  - Floor zones and type-2 zones are both yellow.
  - The legend says lights are gold, but each is drawn in its own colour.
  - The fog rings use `dist_near` as a height around the origin.
- **C9** **Item bank layout is described three ways.** `dat.cpp` says each block is [CLUT][64×152 pixels]; `parse_item_bank` treats it as 128×76; `on_entry_select` says a block's CLUT belongs to the previous item and reads the next block's CLUT, which for the last item is sector padding.
- **C10** **Each decoder handles transparency differently.**
  - README's rule (0x0000 masked, 0x8000 transparent) holds only in the atlas, and there only for DC1: in a DC2 atlas 0x8000 at index 0 is opaque black.
  - Elsewhere: `parse_palette` masks only 0x0000; TIM CLUT entries mask 0; TIM 16bpp never masks; IMD masks 0x8000 only and keeps 0x0000 opaque; `render_linear_8bpp` masks index 0.
  - `bgr555_to_rgba` replicates the top bits, while `tim.cpp`, `texture.cpp` and `decode_bgr555` only shift.
  - `parse_palette` followed by `build_palette` turns 0x8000 into 0x0000 and drops STP bits, and `bgr555_to_rgba`'s comment wrongly claims STP sets alpha.
- **C11** **Message text location.** `rdt_extract_text` scans from the highest header pointer, while README and `scd_disassemble` place the text after the last thread in the SCD block. Its `scd_off` is computed and never used.
- **C12** **Docs and names are out of date.**
  - README says the code is pre-C++11, but it uses lambdas and `{}` init.
  - README promises OpenGL 1.1 with a software fallback, but the atlas has non-power-of-two dimensions, which GL 1.1 (GDI Generic) can't texture.
  - README lists `include/ext/ddraw_ext.h`; the actual file is `pl_mpeg.h`.
  - TODO.md lists Import/Replace, PNG export and entry ownership as missing, but all three exist. "Export as PNG" actually writes BMP.
  - EXPORTING.md, which ships in the release zip, says the zip contains a `source/` folder, which it doesn't. It also says the Windows build is cross-compiled and has never been run on Windows; releases are now MSVC builds made and checked on Windows.
  - The window title and class (`Dino Crisis Archive Tool v2.2`, `DCArchiveToolMain`) and the VS target `DC_Archive_Tool` predate the RaptorScope name.
- **C13** **Cited DINO.exe addresses are from another build (verify).** The handler addresses in comments and README come from a build other than the GOG "Classic REbirth" exe. In that exe, code in 0x422000–0x42BE92 is 0x160 lower than the cited address (0x42A96D is 0x42A80D), and the data addresses (0x657698/0x6576A0, 0x645FA8, 0x62A4C8) do not carry over. Check which build an address is from before looking it up.
- **C14** **`P40` is labelled "T-Rex Boss" (verify).** `app.cpp`'s character name table calls P40 that, but the developer path manifest lists 186 player-style motions for it, and the T-Rex is E10/E11.
- **C15** **DAT entry type 5 is labelled "SEQ music sequence" (verify).** `dat.h`, `dat.cpp` and the tree label say so, but the label rests on `parse_seq_header` accepting a non-zero resolution and a plausible tempo. In the 464 DAT files of the PC game, all 294 type 5 entries pass that test and none contains a SEQ magic.
- **C16** **DC2 overlay data sits in DC1-named fields.** A DC2 room's spawns (0x1A) are in `overlay.items` and its slot-1 markers in `overlay.enemies`, following C1's swapped names; doors, triggers and item pickups are `RDT_ZONE_TRIGGER` zones whose `target_index` (`DC2_ZONE_*`) was chosen to reuse a DC1 zone colour.
- **C17** **`dc1_export` exports DC2 models too.** The name, its usage line and EXPORTING.md's title still say DC1.

### Performance and silent limits

- **P1** **Smooth normals are O(V×F).** `mesh_compute_smooth_normals` compares every vertex with every face and runs on every placed room load. It runs before unplaced sections are appended, so those sections get zero normals.
- **P2** **Opening an archive does redundant work.**
  - `App::build_tree` decompresses each LZSS0 entry up to five times: in `is_mips_code`, `parse_rdt_layout_from_entry`, `is_door_mesh_entry`, `is_weapon_data`, and once more for its label.
  - The first texture view runs `collect_texture_usage` on the UI thread, which fully parses every mesh and EMD in the archive (copying data and extracting clips).
- **P3** **The texture atlas is large and handled inefficiently.**
  - It is `width × 512·slices` RGBA and can exceed 100 MB.
  - It is uploaded with `GL_LINEAR`, which blurs PSX textures (the PSX point-samples); GLB export uses nearest filtering.
  - Its width is never checked against `GL_MAX_TEXTURE_SIZE`, and it is copied a second time into `uv_atlas_rgba`.
  - The viewer also holds each mesh three times: `im_*`, `uv_*` and the caller's copy.
- **P4** **UV editor sort is quadratic.** `ShowUVEditor` uses an O(n²) insertion sort, commented "small N", though rooms have 10K+ faces.
- **P5** **Fixed limits drop data silently.** The limits are:
  - 64 placements/sections (slot masks are u64)
  - 64 zones shared by floor zones and 0x28 trigger zones
  - 32 cameras and 16 characters
  - 16 textures and 16 palettes in the atlas and the face-CLUT renderer
  - 16 EMDs per entry, and 64 `g_emd_info` entries (beyond that, selecting EMD n shows EMD 1)
  - a 2000×2000-cell walk grid
- **P6** **VM/software detection misfires on real machines.**
  - It triggers on registry disk names containing "Msft"/"Virtual", and on GL strings containing "D3D" or "Mesa" or vendor "Microsoft" (which GLon12 reports).
  - When it misfires, lighting, culling and textures are turned off.
- **P7** **Walk mode is simplistic.** It keeps a single `walk_floor_y` (no stairs or levels, even though `floor_below` exists for camera shots) and uses a fixed dt of 0.016 s whatever the timer rate.
- **P9** **DC2 fixed limits.** 64 routines per script (the largest room has 30), 32 pushes per record (a door uses 19), 128 collision polygons and 1024 points (largest room: 32 and 210), 64 zones shared by slot-7 zones, doors, triggers and items (largest room: 33), 64 spawn records scanned and 32 drawn (ST202 has 48 records; the most drawn in one room is 13), 50 model parts (the largest model has 21). Anything beyond is dropped silently, as in P5. `App::build_tree` decompresses every DC2 LZSS0 entry once to label it.
- **P8** **Save editor setup re-enters the app.** `SavePanel_FinalizeDark` pumps messages from inside `switch_panel` before the save is loaded, so input during its progress popup re-enters the app.
